# Dentory iOS: how to build a ticket

The house standard for Dentory's Swift code. Where a ticket and this skill disagree, the ticket wins for product behaviour and this skill for code structure. The reasons, the folder tree and worked examples are in `docs/handoff/ios-architecture.md`. Load `swiftui-pro` to review SwiftUI diffs and `swift-concurrency` for Swift 6 concurrency errors.

## 1. Workflow

1. Read the issue, every frame it lists (`design/frames/fNN*.png`), its prototype screen key, its PRD section and the MS-100 (#71) decisions that touch it. Do not start while a blocker is open.
2. Branch `ms-1NN-short-name` from the default branch: one ticket, one branch, one PR.
3. Put the code in the ticket's feature folder (section 2), creating it for a feature's first ticket.
4. Write the view model tests first (section 6), then the view model, then the view. Set the PRD Appendix B id as `.accessibilityIdentifier` on every interactive element.
5. Before pushing: `make lint`, `make test WARNINGS_AS_ERRORS=YES`, a build for the iPhone 16 and iPad Pro 11-inch simulators, the UI flows the ticket changes, `make e2e` when it touches a journey the end-to-end flows drive (or the database or Edge Functions under one), and the `swiftui-pro` review of the SwiftUI diff with its genuine findings fixed. `docs/handoff/mac-tooling.md` lists what CI rejects that the Mac accepts.
6. Open the PR from `.github/pull_request_template.md`: title `MS-1NN · …`, `Closes #N`, simulator screenshots next to the frame images, and a note wherever the frame was followed over the PRD. Then stop at green CI and report: the build thread runs the review loop in `CLAUDE.md` and resumes you with any findings.

## 2. Layout

- `App/` holds the app entry, `AppDependencies` and the root views. `Core/DesignSystem` is the only place colors, fonts and sizes live (`MS` is its prefix: `MSButton`, `MSSheet`); `Core/Domain`, `Core/Data`, `Core/Navigation` and `Core/Support` hold shared types, data plumbing, routing and formatters.
- `Features/<Feature>/` owns that feature's views, view models, repository protocol and Supabase implementation, and routes. Keep it flat; add subfolders only past about 12 files.
- Tests mirror it in `DentoryTests/Features/<Feature>/`; UI flows live in `DentoryUITests/`; migrations, functions, seed and pgTAP tests in `supabase/`. The `.xcodeproj` is generated by `make project`, never committed.
- One type per file, named after the type.
- A feature never imports another feature's internals: shared types move to `Core/Domain`, shared UI to `Core/DesignSystem`, and navigation between features goes through route values (`InventoryRoute.product(id)`), never another feature's view model.

## 3. Layers

View owns ViewModel, which calls a Repository protocol, implemented by `Supabase<Name>Repository`.

- **View** (`struct …View: View`): renders state and forwards intent; no business rules, networking or formatting beyond calling a formatter. Owns `@State private var viewModel` built from injected dependencies, loads with `.task { await viewModel.load() }`, uses only design-system tokens and components (no `Color(red:…)`, hex, font names or magic paddings), and keeps `body` short with subviews as separate structs, not computed properties.
- **ViewModel** (`@MainActor @Observable final class …ViewModel`): one per screen, or per sheet that has its own logic. Screen state as stored properties, `private(set)` unless the view binds to them, plus a `LoadState` enum when it loads. Intent methods named after the user action (`startProcedure()`). Depends only on protocols passed to `init`, never a global or singleton. Imports `Foundation` and `Observation`, never `SwiftUI`. Derived values are computed properties, not duplicated state.
- **Repository** (`protocol …Repository: Sendable`): the boundary to Supabase, one small protocol per aggregate the feature uses, not one API client. Methods are `async throws` and return domain types, never DTOs or JSON; the Supabase implementation maps DTOs in one place. Stock changes call the MS-106 RPCs with an idempotency key; never insert into `batches`, `transactions` or `open_items`.
- **Domain** (`struct`, `Sendable`, `Equatable`): value types with the rules that belong to the data (`ProductStatus.evaluate`); no Supabase or SwiftUI imports.
- **Composition root**: `AppDependencies` holds one instance of each repository and service, built live in `DentoryApp` and with fakes in tests and previews, passed through an `EnvironmentKey`; views hand their view model the pieces it needs. Only it knows the concrete Supabase types.
- `final class` for view models and services; `struct` for models, DTOs, views and routes; `enum` for states, routes and closed sets.

## 4. Swift and SwiftUI

- `project.yml` build settings stay as they are (Swift 6 mode, complete strict concurrency, default `MainActor` isolation, approachable concurrency, iOS 17.0, iPhone and iPad). Use `nonisolated` or `@concurrent` only where profiling shows it matters.
- `async`/`await` only: no completion handlers, no Combine. Observation only: never `ObservableObject`, `@Published` or `@StateObject` in new code.
- One `NavigationStack` per tab with a typed path; sheets through `.sheet(item:)` driven by an optional enum on the view model.
- Throw `AppError` (`.network`, `.notFound`, `.forbidden`, `.readOnly`, `.validation(field:message:)`, `.unknown`); the view model maps it to MS-108's copy ("Couldn't save. Try again.").
- Copy follows the `CLAUDE.md` rules; strings live in `Localizable.xcstrings` (English only in V1.1).
- Every control has an accessibility label; Dynamic Type works up to the Large step.
- iPad uses the same tabs and screens with content capped at 720 pt and centred (MS-103's container); iPhone is portrait only.
- Money, dates and quantities go through the `Core/Support` formatters with the clinic's currency and time zone.

## 5. Do not

- No VIPER, use-case layer, Coordinators, TCA, Redux stores or Combine pipelines.
- A protocol only at a real boundary (repositories, `Clock`, `NetworkMonitor`, `Analytics`, `ImagePicker`), never for view models, views, formatters or models. No generic `Repository<T>`, no `ViewModelProtocol`, no factories for things built once, no plugin registries: a new status or alert type is a new enum case handled with `switch`.
- No inheritance hierarchies (`BaseViewModel`, abstract superclasses): compose, and share behaviour through small protocol extensions or helper types.
- No third-party package without a ticket saying so (in the app: `supabase-swift`, Sentry, PostHog).
- No feature, flag or setting the ticket does not ask for.
- Soft limits: a view about 150 lines, a view model about 250; past that, split by responsibility.

## 6. Tests

- Swift Testing (`@Test`) for every view model and domain rule, with hand-written fakes (canned results, recorded calls) that fail the way the Supabase implementation does; no mocking frameworks. Test names read as behaviour (`startIsDisabledWhenNoItemsSelected`).
- One XCUITest flow per user journey the ticket changes, finding elements by Appendix B id, against the local stack seeded with the demo clinic (MS-109).
- A pgTAP test for every migration, RLS policy and RPC.
- A ticket is not done while any test is red or skipped.

## 7. PR checklist

- [ ] Code sits in the right feature folder; no cross-feature imports.
- [ ] View has no business logic; view model has no `SwiftUI` import; repository returns domain types.
- [ ] Stock changes only through MS-106 RPCs with an idempotency key.
- [ ] Only design-system tokens and components in feature code.
- [ ] Appendix B ids on every interactive element.
- [ ] Unit tests for the view model and domain rules; UI test updated when a flow changed; SQL tests for database changes.
- [ ] Builds clean with zero warnings in Swift 6 mode; SwiftLint clean.
- [ ] Nothing in section 5 was introduced.
